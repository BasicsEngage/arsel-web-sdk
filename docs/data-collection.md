# Data collection

What the SDK stores, what it sends, and what it never touches. Written to be answerable to a
security review or a DPA questionnaire without anyone reading the source.

## What it stores in the browser

All of it in **IndexedDB**, database `arsel`. No cookies. No `localStorage`. Nothing is written to
another origin, and nothing is readable cross-origin.

| Key | What | Set by | Cleared by |
| --- | --- | --- | --- |
| `client_key` | your publishable `pub_…` key | `init()` | — |
| `base_url` | your API base | `init()` | — |
| `anonymous_id` | a random UUID naming the person | first `init()` | rotated by `reset()` |
| `external_id`, `email`, `phone_number` | whatever **you** passed to `identify()` | `identify()` | `reset()` |
| `installation_id` | a random UUID naming this browser profile | first push subscribe | — |
| `device_secret` | authenticates engagements | push registration | — |
| `vapid_key_version`, `endpoint` | push subscription bookkeeping | push subscribe | — |
| `session_started_at`, `backgrounded_at` | session boundaries | visibility changes | `reset()` |
| `last_response_*` | diagnostics: status code, path, timestamp | every request | — |
| *events store* | queued events not yet delivered | `track()` | on delivery |

Every id is generated by `crypto.randomUUID()`. None of them is derived from anything about the
device or the user.

### Why IndexedDB and not cookies

The service worker has to read this state to report a `delivered` when **no tab is open**. Cookies
aren't the right tool, and `localStorage` is unreachable from a worker. A consequence worth knowing:
none of it is sent automatically with your own requests, and none of it is visible to another site.

## What it sends

Only to the `baseUrl` you configure. No third-party hosts, no analytics vendors, no CDN calls at
runtime, and `credentials: 'omit'` on every request, so no cookies ride along. Every request
carries an `X-Arsel-SDK: web/<version>` header identifying the SDK build, and event requests carry
an `Idempotency-Key` (a random UUID per event, minted locally) so retries are not double-counted.

### With every event

| Field | |
| --- | --- |
| `event` | the name you passed |
| `data` | the properties you passed |
| `anonymous_id` | always — it is what the backend merges from |
| `external_id` / `email` / `phone_number` | only if **you** supplied them to `identify()` |
| `timestamp` | ISO-8601, from the browser clock |

### With a push subscription

| Field | |
| --- | --- |
| `installationId` | the random UUID above |
| `anonymousId` | the same random UUID the events API sends — it binds the subscription to the contact |
| `endpoint`, `keys` | issued by the browser's push service, posted verbatim |
| `platform` | `"web"` |
| `enablementStatus` | whether permission is currently granted |
| `deviceTimezone` | IANA zone, e.g. `Asia/Riyadh` — used for send-time scheduling |
| `deviceLocale` | e.g. `ar-SA` — used for language selection |

## What it does **not** collect

Explicitly, because these are the questions that get asked:

- **No fingerprinting.** No canvas, WebGL, audio, font enumeration, or hardware probing. The ids are
  random, not derived.
- **No IP-based geolocation, and no Geolocation API.** The SDK never calls `navigator.geolocation`.
- **No page content.** No DOM scraping, no form values, no keystrokes, no session replay.
- **No automatic page views.** Nothing is tracked that you did not call `track()` for, other than the
  three `arsel.*` session and identify events.
- **No contact list access.** The client key cannot read anything — it authenticates writes on two
  channels and nothing else.
- **No cross-site tracking.** Storage is origin-scoped; there is no shared identifier across
  customers, and no third-party cookie.
- **No advertising identifiers.**

Whatever you put in event properties, the SDK sends. It does not inspect or redact them — see
[the guidance on what not to put in a property](events.md#what-not-to-put-in-a-property).

## Consent

The SDK does nothing until `init()` is called, and it prompts for nothing until `promptForPush()` is
called. Both are yours to gate.

Under GDPR-style regimes, the common shape is:

```js
if (consent.analytics) {
  await Arsel.init({ clientKey, baseUrl });
}
```

If consent is withdrawn later, stop calling `track()` and call `reset()` to rotate the identity and
drop the stored identifiers. To remove the local state entirely:

```js
indexedDB.deleteDatabase('arsel');
```

Notification permission is separately governed by the browser and revocable by the user at any time,
without your involvement.

## Erasure and export

Local state is one `deleteDatabase('arsel')` away. Server-side, a contact's events and profile are
subject to your org's retention settings and to the erasure API — deleting the browser's copy does
not delete what was already delivered, and shouldn't be presented to a user as if it does.

## Data residency

The SDK sends to the `baseUrl` you configure and nowhere else. Where that data then lives is a
property of your Arsel org, not of the SDK.

## Subprocessors introduced by push

Web push necessarily routes through the browser vendor's push service — Google (FCM) for Chrome,
Mozilla for Firefox, Apple for Safari. That is how the Web Push standard works and is not
SDK-specific, but it belongs in your subprocessor list. Payloads are encrypted end-to-end with the
subscription's own keys, so those services relay ciphertext, not your message content.
